1. The brief, and what it really asks

Lesson page, section 18

Train a 20M LLM for 50M tokens on Google Colab. Fix a batch size you can run.

Train again with reversibility (report which variant worked: midpoint, euler, etc).

Train again with reversibility, pushed to the maximum batch size.

Report final loss, speed (tokens/s), peak memory and other findings.

What that means in practice

Four runs of 50M tokens: baseline, two reversible variants at the same batch, then the better variant at its largest batch.

The interesting number is the batch ratio: how much bigger a batch fits once activations stop being stored. The paper measured 9.88× on an H100.

The trap: on a 20M model the biggest memory user is often the logits, which reversibility does not touch.

With GPT-2's vocabulary, one sequence costs about 245 MiB of logits against 102 MiB of block activations (option C). Unless the loss is computed in chunks, or the vocabulary is smaller, reversibility would free the smaller half and the headline result would be "it barely helps" — a finding about the output layer, not about reversibility.

Flag — "maximum batch" runs into a second limit

The token budget is fixed at 50M. A batch of 1514 sequences of 512 tokens is 775k tokens per step, so the whole run would be about 64 optimizer steps. The model would hardly train, and the final loss would be poor for a reason that has nothing to do with reversibility.

Three honest ways to handle it, your call in decision 4: report the true maximum and explain the step count; cap the batch so the run still takes a sensible number of steps; or hold the batch and spend the freed memory on a longer sequence instead.

3. Decisions I need from you

Everything else follows from these. Where I have a recommendation it is marked; the reasoning is in Part 2 of the report.

Settled already decided

  • Hardware: Colab T4, free tier. That fixes fp16 with a loss scaler (no bf16), sequence length 512, and a ceiling of about 15 GB for the batch search.
  • Dropout is 0 in every run, including the baseline.
  • The memory saving comes from a custom backward pass, not from the equation.

Why dropout has to be 0

Dropout is a training trick. Each time a layer runs, it picks a few of the numbers at random and sets them to zero, so the model cannot lean on any single one. Which numbers get zeroed changes every time.

That breaks a reversible model. Its backward pass does not read stored activations; it runs the layer again and subtracts the answer to get back to the earlier state. For that to work, the layer must give the same answer both times. With dropout on, the second run zeroes different numbers, so it returns a different answer, and the state we rebuild is wrong.

Nothing crashes when this happens. The gradients are simply a little wrong, the loss curve looks plausible, and you would never know. So dropout is off.

Why the baseline also runs with dropout off: if only one of the two runs used dropout, part of the difference in loss would come from dropout rather than from reversibility, and we could not say which. Turning it off everywhere keeps the comparison clean. We lose nothing, because we read 50M fresh tokens once and never repeat them, and dropout mainly helps when a model sees the same text many times.

Worth knowing

This is a limit of how these methods are written, not a law of nature. You could save the random seed for each layer and replay the same pattern on the rebuild, which is what PyTorch's activation checkpointing does. But the reversibility paper and the instructor's Lightning LM report both require dropout 0, so we follow them instead of inventing a variant.

Why the saving needs a custom backward pass

When you write normal PyTorch code, PyTorch quietly keeps every intermediate number that the backward pass will need. That stored pile is the activation memory, and it grows with every layer you add.

So if you write the reversible rule as ordinary code, you get the reversible maths and none of the benefit. PyTorch still keeps everything, for all 16 layers, plus the extra states the rule needs. Memory goes up, not down. This is the easiest way to get a null result on this assignment.

The saving comes from taking over the backward pass ourselves, with a torch.autograd.Function:

  1. The forward pass runs with graph-building switched off, so nothing is stored. It keeps only the two states at the ends of the stack.
  2. The backward pass walks down from the top layer. For each layer it rebuilds that layer's input from the state above, runs that one layer again with gradients switched on, takes the gradients, and then throws that layer's working numbers away.

Peak memory is then the two end states plus one layer, instead of all 16. The price is that every layer runs a second time, which is where the 30–50% slowdown comes from.

How we check it is right. Two gates run before any long training:

  • Gradient gate: run the same model twice, once the ordinary way and once through our custom backward pass, and check the gradients match. Done in double precision on the CPU, where they should agree to many decimal places.
  • Reconstruction gate: compare each rebuilt state against the real one and report how far it drifts in 16-bit arithmetic. This tells us whether the residual stream needs to stay in 32-bit.

If either gate fails, nothing below it can be trusted, so we fix it before spending time on Colab.

1 · What "20M" means decided 20 Sep

How to read a shape like "16 × 320"

16 layers, each carrying a token as 320 numbers. Same notation as the lesson's 96 × 5,120 model. The first number is depth (how many transformer blocks the token passes through); the second is width, the hidden size, the length of the vector that represents one token between layers — the residual stream that reversibility rebuilds.

Everything inside a block follows from the width: attention splits it into heads (320 = 5 heads × 64; the lesson's 5,120 = 40 × 128), and the feed-forward expands it about fourfold and back (320 → 1,280 → 320; the lesson's 5,120 → 16,384 → 5,120). The weights in one block come to roughly 12 × width²: Q, K, V and O are width × width each (4 × width²), and the two feed-forward matrices are width × 4·width each (8 × width²). So 12 × 320² ≈ 1.23M per block, × 16 layers = 19.7M.

The shape does not include the sequence length (512, settled) or the batch size (the thing being measured). Those describe the data flowing through, not the model.

Why depth is the lever here: reversibility removes one stored activation per layer, so 24 layers have three times as much to give back as 8. Width and vocabulary matter for a different reason: the vocabulary sets how big the logits are, and logits are the one thing reversibility cannot shrink.

3 · What the second reversible run should be decided 21 Sep

Already settled by the class

The technique is reversibility with the midpoint rule. The lesson page covers only midpoint. In class the instructor said "we are going to be using midpoint", that they found it "works much better", and his Lightning LM models use the reversible midpoint stack.

So midpoint is fixed. It is your main reversible run.

Left open by the class

What the comparison run is. The brief asks you to "report which variant worked for you (mid-point, euler, etc)", and in class he said to test Euler and midpoint and judge by the loss curves.

But he never said what the Euler variant is, and plain Euler is the ordinary residual rule, which cannot be run backwards. That one word is the only gap.

So this decision is not "pick a technique". It is narrower: what should the second, "Euler" run actually be? The simplest way to close it is one line to the instructor: "By Euler, do you mean the bootstrap or a separate integrator, and where does a = 0.5 enter the update?"

The brief says "mid-point, euler, etc". Plain Euler is the ordinary residual block, which is not reversible, so "Euler" has to mean one of two things:

  • Midpoint vs the Hamiltonian / symplectic-Euler coupling recommended — two genuinely different reversible architectures. The second is the RevNet-style two-stream rule and is fairly called an Euler variant.
  • Midpoint with two bootstraps (Euler kick vs no kick) — this is the Lightning LM config naming, but it compares a starting detail, not two architectures.
  • Add leapfrog as a third run (the paper's second-order rule), about 15 extra minutes.

What Lightning LM actually did

Lightning LM is the instructor's own model family, and it is what he showed at the end of the session. Its report (lightninglm.theschoolofai.in) has a whole section called "Reversibility as the Backbone". Useful facts for us:

The gap I keep hitting

The site writes the update as next = x + δ(x + ½·δ(x)). That is the textbook midpoint step, and on its own it is not reversible: you still cannot get x back from next. The reversible version is the two-state form from the paper, next = previous + 2h × block(current). Where their coefficient a = 0.5 enters is not written down in anything I can read, and I could not find the library.

So either you can get the library or the formula through the course, or I implement the paper's two-state midpoint and treat the step size as the one knob, chosen by a short sweep over a few hundred steps.

So: do you have the course's reversible library, or the exact form of the blend coefficient a = 0.5 that Lightning LM uses? Neither the paper nor the public report pages give the equation it enters, and I would rather use the real thing than guess. Without it I implement the paper's plain midpoint and choose the step size with a short sweep.

4 · Batch sizes, learning rate and weight decay decided 21 Sep

This decision has four small parts. They all come from one fact: the number of training tokens is fixed at 50M.

The fact that drives everything

One training step reads one batch. So the number of steps is fixed by the batch size:

steps = 50,000,000 tokens ÷ (batch × 512 tokens per sequence)

Bigger batches mean fewer steps. Each step is a better estimate of the right direction, but there are fewer of them, and a model needs enough steps to learn. Below a few hundred steps, a model this size barely gets going, whatever its memory tricks.

Part a · The baseline batch (runs A, B and C)

The brief says "fix a batch size you can run". Two ways to read it:

  • A comfortable batch, such as 32 recommended — about 3,050 steps, so all three runs train properly and their loss curves are easy to compare. It also leaves plenty of room to show how much bigger reversibility lets the batch go.
  • The baseline's own maximum (about 150 by my estimate) — the fastest baseline in tokens per second, but only about 650 steps, and very little room left above it before run D hits the step problem below.

Part b · What "maximum batch" means for run D

My estimate for the reversible model's true maximum is about 1,500 sequences, which leaves only about 64 steps. Run D would then show a worse loss for a reason that has nothing to do with reversibility.

  • True maximum — push until memory runs out and train there. Honest and loud about memory, but the loss result is mostly about having too few steps.
  • Measure the true maximum, train at a capped batch recommended — find the real maximum with a short probe (no training, so it costs a minute), report it as the memory result, and train run D at the largest batch that still leaves at least about 400 steps (around 240 sequences). You get both answers: how far memory goes, and what a much bigger batch does to training.
  • Spend the memory on longer sequences instead — keep batch 32 and raise the sequence length to 2,048 or 4,096. A different way to show the saving; it changes the brief's question, so I would only add it as an extra.

Part c · Learning rate for the bigger batch

With fewer, better-averaged steps, the same learning rate moves the model a shorter total distance. The usual fix for Adam-style optimizers is to raise the learning rate by the square root of how much bigger the batch got: 8 times the batch means about 2.8 times the learning rate.

  • Square-root scaling recommended — standard, one number, no extra runs.
  • Keep the same learning rate — simplest, but run D will probably under-train, and you cannot tell whether that is the batch or the learning rate.
  • Short sweep — try 3 learning rates for a few hundred steps each and pick the best. Most reliable, about 15 extra minutes.

Part d · Weight decay

Weight decay pulls every weight a tiny step towards zero at each update, which keeps weights from growing too large. The instructor said reversible runs should not use it. The paper and the Lightning LM report do not say that; they only require dropout 0. It does not break the rebuild, because it happens in the optimizer after the backward pass.

  • Same value in all four runs, such as 0.1 recommended — the usual setting, and fair because every run gets it.
  • 0 in all four runs — follows the instructor's advice exactly, and still fair. On 50M tokens the difference will be small.
Decided — 21 Sep, and why

a · Batch 32 for runs A, B and C. At 32 sequences each run takes about 3,050 steps, which is plenty for a 20M model to train properly, so the three loss curves can be compared fairly. It also leaves a lot of memory unused on purpose: that unused room is exactly what run D will fill, which makes the effect of reversibility easy to see. If we started at the baseline's own maximum (about 150), there would be almost no room left above it before running into the step problem.

b · Run D: measure the true maximum, but train at a capped batch of about 240. The true maximum (about 1,500 by estimate) would leave only about 65 steps, so its loss would mostly show "not enough steps", not "reversibility". So we split the question in two. A one-minute probe, with no training, finds the real largest batch for both the baseline and the reversible model; the ratio between them is the memory result, the same kind of number as the paper's 9.88×. Run D then trains at the largest batch that still gives about 400 steps (around 240 sequences, roughly 8× the baseline). That shows what a much bigger batch does to speed and loss, without the step count ruining the result.

c · Learning rate scaled by the square root of the batch increase. A bigger batch means fewer steps, so with the same learning rate the model moves less far in total and ends up under-trained. Raising the learning rate by the square root of the batch ratio is the standard correction for Adam-style optimizers: about 2.8× for an 8× batch. It is one number with no extra runs, and it means a worse loss in run D can be put down to the batch, not to a learning rate we forgot to adjust.

d · Weight decay 0.1 in all four runs. It is the usual setting, and giving every run the same value keeps the comparison fair. The instructor advised against weight decay for reversible runs, but neither the paper nor the Lightning LM report requires it, and it cannot break the rebuild because it happens in the optimizer, after the backward pass. The report will mention his advice, and if the reversible runs misbehave, weight decay 0 is the first thing to try.

What this already shows. The reversible models slow down by about a fifth, not the 30–50% the paper estimates. Doubling the depth from 8 to 16 layers adds 1,500 MiB to the ordinary model and under 40 MiB to the reversible ones: memory that does not grow with depth, measured.

The gates on the GPU. In 16-bit arithmetic the rebuilt states drift more than on the CPU: the error is tiny at the top of the stack (4e-8) and grows to about 2e-3 by the bottom layer, for both stacks. The likely reason is that the GPU does not produce bit-identical results when it re-runs a layer during the backward pass, so each rebuild adds a small error that builds up going down. The gradients still agree with plain PyTorch to a cosine of 0.99995, so training is not harmed, but it is worth a line in the report, and it is the first thing to suspect if the reversible runs trail run A in the full run.

Two things the numbers exposed

1 · Midpoint pays for one extra layer, and it is my implementation, not midpoint. Midpoint uses exactly 162.9 MiB more than two-stream, at both 8 and 16 layers. A gap that does not grow with depth is one stored layer. It is the Euler start: the single ordinary step that makes midpoint's second starting state runs outside the reversible stack, through normal PyTorch, so it stores that layer's working numbers. That is why midpoint fits 664 and two-stream 912. Proposed fix: re-run that one step during the backward pass instead of storing it, the same trick as the rest of the stack.

2 · The probe is slightly optimistic. Each extra reversible layer adds exactly 4.7 MiB, which is that layer's weights and nothing else. The probe measures the first training step, and Adam creates its two running averages only at the end of that step, after the peak. In real training they already exist, adding 171 MiB. Proposed fix: the probe takes two steps and measures the second. Run D is unaffected (240 is far below the limit), but the reported largest batch and the per-layer figure will be honest.

Side check, midpoint start: the plain start beat the Euler start by 0.054 in these 60-step runs. That is too short to trust, but together with point 1 it bears on decision 3, so it is raised below as an open question.

23 Sep · the first smoke run found a bug, now fixed

What happened. Everything up to run D worked on the T4: the data, the three gates, the step-size sweep, the memory probe, and runs A, B and C. Run D then crashed with IndexError: list index out of range the first time it tried to print its progress.

Why. The training loop wrote down the training loss every 25 steps, and evaluated the model every 0.5M tokens (2.5M in the full run). Each evaluation line prints the latest training loss. Run D's batch is 3 times bigger, so it reached its first evaluation at step 10, before step 25, when no training loss had been written yet. The CPU test never hit this, because there the evaluation always came after the first log step. The full run's run D would have crashed the same way at step 20, so this is exactly what the smoke run is for.

The fix. The training loss is now also written down at every evaluation, and the print never reads an empty list. Tested on the CPU with the log interval set so that every evaluation comes first, which is the exact failing condition: run D finishes, all checks pass, and the validation losses are identical to before, so the fix changes only what is logged.

What a re-run costs. The data, the gates and the memory probe reload from Drive. The sweep and runs A to D are retrained, because their cache fingerprint includes the training loop's code and that code changed. In smoke mode that is a few minutes.

A first real number, as a side effect. The crash message shows run D's memory limit as 816, which is 90% of the largest batch the probe found for the winning reversible variant. That puts its largest batch at 912 sequences. My estimate was about 1,500, so the real headroom is smaller than estimated. The full probe table will show why.

Two things added while building, both following from earlier decisions:

  • The loss is computed in slices of 8,192 tokens, recomputed during the backward pass. Without it, at run D's batch of about 240, the scores over the vocabulary alone would take several GB and would drown out the memory we want to measure. Every run uses it, so the comparison stays fair.

Group 2 · Data (Cell 4) · about 10–20 minutes, once

build_data() streams FineWeb and does four things in order:

  1. keeps the first ~6M characters of documents aside as validation text, never trained on;
  2. trains a byte-pair tokenizer with 8,192 tokens on the next ~40M characters;
  3. turns the validation documents into 1M tokens (val.bin) and the training documents into 50.5M tokens (train.bin, about 100 MB), each stored as 16-bit numbers;
  4. saves everything to Drive with a meta.json, so this never runs again.

Windows then cuts the training tokens into 98,632 pieces of 513 tokens and shuffles their order once with a fixed seed. Every run reads the pieces in that same order, so all four runs see identical data.

round trip       : ... tokens -> 'Reversible networks rebuild their activations instead of storing them.'

Group 3 · The model (Cells 5–6) · instant

Cell 5 defines one transformer block. Its method Block.delta(x) is the f(x) from the lesson: everything one block adds to the stream. GPT.states() then stacks 16 blocks in one of three ways:

# run A, ordinary:          x = x + f(x)
# run B, midpoint:          a, b = b, a + 2h * f(b)
# run C, two-stream:        q = q + h * Attn(p);  p = p + h * MLP(q)

All three start from the same weights (make_model() resets the seed first), so differences come only from the stacking. chunked_ce() computes the loss in slices of 8,192 tokens so the vocabulary scores never all exist at once.

Cell 6 is where the memory saving lives. MidpointStack and TwoStreamStack each have their own forward and backward pass:

forward:   with torch.no_grad():              # build no graph, store nothing
               for blk in blocks:  a, b = b, a + 2h * f(b)
           keep only (a, b) at the top

backward:  for blk in reversed(blocks):       # walk down
               y   = f(a)          # run this one layer again, with gradients on
               prev = b - 2h * y   # rebuild the earlier state by subtracting
               grads = autograd.grad(y, ...)  # this layer's gradients
               # the layer's working numbers are dropped here
parameters: 22,467,200 (training state 343 MiB)

Group 5 · The training loop and the sweep (Cells 10–11) · smoke 2–4 min, full 6–10 min

Cell 10 defines train_run(), used by every run: AdamW, warm-up then cosine learning rate, fp16 autocast with loss scaling, gradient clipping at 1.0. It prints one line per evaluation. Speed is timed on the GPU clock over training steps only (not the first 10 steps, not the evaluations). Peak memory is PyTorch's own counter. It saves a checkpoint every 8 minutes, and cached_run() makes a finished run reload instead of retraining.

Cell 11 runs short training runs to pick the step size h: midpoint at 0.25, 0.5 and 1.0, two-stream at 0.5 and 1.0, then the side check that picks midpoint's start. It ends with a small table, "← chosen" next to the winners, and one sentence saying which start run B will use. The rule, fixed on 23 Sep before any full-run result: the Euler start stays unless the plain start is better by more than 0.02.

Group 6 · The memory probe (Cell 12) · about 5–10 minutes

_largest_batch() tries one full training step at batch 8, 16, 32, 64… until it runs out of memory, then narrows the gap. Running out of memory is expected and caught by _try_step(), so you will not see red errors. Then it measures one step at each depth in ProbeCfg.depths.

  largest batch, ordinary  :  ...
  largest batch, midpoint  :  ...
  largest batch, two-stream:  ...
  midpoint fits ...x the ordinary model's largest batch
  ordinary   grows ... MiB per extra layer
  midpoint   grows ... MiB per extra layer

What to expect, from the smoke run: the smoke probe measured 144 for the ordinary model, 664 for midpoint and 912 for two-stream. The full run should differ in two ways, both from the 23 Sep fixes. Midpoint should rise to about two-stream's figure, because its Euler start no longer stores a layer. All three should drop a little, because the probe now measures the second step, when Adam's running averages exist, as in real training. For memory against depth, the ordinary model should still grow by roughly 190 MiB per extra layer; the reversible ones should now grow by about 10–19 MiB instead of the smoke run's 4.7, because that layer's optimizer state is now counted.
