2. Why this session exists: storage versus compute

Session 12's ZeRO divides what each GPU stores: optimizer state, gradients, and finally weights. Every GPU still runs the whole model on its own micro-batch, layer 1 to the last layer. Three problems remain:

  1. ZeRO never divides activations. One 8,192-token sequence through the course's 30B model stores 127.5 GiB of activations. An H100 holds 74.5 GiB. Even with the training state fully sharded, that one sequence does not fit.
  2. ZeRO-3 rebuilds every full layer, every step. It needs a whole layer to fit on one GPU, and gathering it costs traffic.
  3. A single long sequence cannot be split by data parallelism. 131,072 tokens produce 2,040 GiB of activations, and that is one sample. Adding data-parallel copies does nothing for it.
Carry forward

Session 12 answered "the model's state does not fit". Session 13 answers "the model's computation does not fit". Real runs use both at once.

3. First pass: a recap of ZeRO, and the ZeRO-3 confusion

He explained the whole session twice: a quick intuitive pass, then a detailed pass with numbers. The first pass used a textbook analogy: the model is a 1,000-page book and 8 GPUs are 8 students.

  • Data parallelism: every student gets the full book and studies different examples. Fast, but everything is copied 8 times.
  • ZeRO-1: each GPU keeps 1/8 of the optimizer state. ZeRO-2: also 1/8 of the gradients. ZeRO-3: also 1/8 of the weights.

A student had asked why their assistant said ZeRO-3 "has one layer per GPU". The answer is the key point of the first half: under ZeRO-3 each GPU stores 1/8 of the weights, but still computes the full layer. Before layer 17 runs, every GPU gathers the other 7/8 of layer 17, computes the whole layer on its own micro-batch, then throws the borrowed pieces away.

Carry forward

ZeRO-3 divides model storage, not the matrix multiplication.

4. First pass: tensor parallelism

Tensor parallelism (TP) splits the matrix multiplication itself. A layer's weight matrix is cut into 8 slices, one per GPU. A token enters, each GPU multiplies it by its own slice, and the GPUs exchange their partial results to form the full output. Weights stay where they are; only computed results travel.

He gave a reason it helps beyond memory. If a GPU can comfortably work on a 1,000×1,000 block and you hand it 8,000×8,000, it does not fail; it just works through the 64 blocks one after another. Splitting across GPUs lets each one handle a piece in parallel.

Jargon — tensor

A tensor is a multi-dimensional array; a matrix is a 2-D tensor. "Tensor parallelism" means splitting the weight matrices.

Flag — the 64-step analogy

The 1,000 vs 8,000 example is a teaching simplification. Real GPUs already tile every large matrix multiply internally. The practical reasons for TP are that one layer's weights and activations are too big for one GPU and that it spreads the compute across more GPUs working on the same sample.

5. First pass: sequence parallelism

Picture one layer's activation as a grid: 4,096 tokens (rows) by 8,192 hidden values (columns). TP splits the columns inside attention and the feed-forward block. But between those blocks sit small operations that work on each token separately: layer normalization, dropout, and residual additions. Without help, every GPU runs those on all 4,096 tokens and stores the result in full.

Sequence parallelism (SP) splits the rows for just those operations: GPU 0 handles tokens 1–512, GPU 1 tokens 513–1,024, and so on. He stressed the limit: SP does not mean GPU 0 processes tokens 1–512 end to end. It only takes those per-token operations.

Jargon — dropout, layer norm, residual
  • Dropout: during training, randomly set a fraction of values to zero (for example 5%) so the network cannot rely on any single neuron. He drew 3 inputs to 4 outputs and zeroed one output at random.
  • Layer normalization: rescale each token's vector so its values have a standard mean and spread.
  • Residual connection: add a layer's input back onto its output, x + f(x).
All three act on each token independently, which is why they can be split by token.

6. First pass: pipeline parallelism

Pipeline parallelism (PP) cuts the model by depth. With 96 layers and 8 GPUs, GPU 0 owns layers 1–12, GPU 1 owns 13–24, and so on. A batch flows through them like an assembly line. Unlike ZeRO-3, GPU 0 never computes layers 13–96.

He asked the class to picture it running: while GPU 1 works on batch 1's layers 13–24, GPU 0 is already doing layers 1–12 of batch 2. The line only becomes fully busy once enough micro-batches have entered.

7. First pass: context parallelism

Context parallelism (CP) sounds like SP but solves a different problem: one very long sequence, say 128,000 tokens. With CP = 8, GPU 0 is fully responsible for tokens 0–15,999, GPU 1 for the next 16,000, and so on, through every layer. That is the difference from SP, which only took the small per-token operations.

The catch is attention: a token on GPU 7 must look at earlier tokens on GPU 0 (for example, the system prompt). So GPUs exchange the keys and values of their tokens, and nothing else.

Jargon — keys, values, KV

In attention every token produces a query ("what am I looking for"), a key ("what do I contain") and a value ("what I pass on"). Other tokens only need your key and value, so KV is all that must be shared. The same KV idea returns later as the KV cache in inference.

A student asked what separates layer-splitting from token-splitting, since "data is split either way". His answer: they split different things (layers vs tokens) and you must decide deliberately which to use; CP is what enables long-sequence training.

8. The whole picture: five axes, and a 64-GPU example

Why ZeRO-3 doesn't solve everything. Take a 1-trillion-parameter model and enough GPUs that ZeRO-3 makes the weights fit. Now ask for a 256K-token context. ZeRO has nothing to offer, because the problem is activations. You then need CP for the tokens, SP for duplicated activations, TP for the huge matrices, and PP for 100+ layers.

The 64-GPU example. 64 GPUs as TP = 8 × PP = 4 × CP = 2. The pipeline has 4 stages of 16 GPUs each. Inside a stage, the 16 GPUs form 2 context groups (first half of the tokens, second half), and each context group is 8 GPUs doing tensor parallelism. With 512 GPUs you copy that whole 64-GPU arrangement 8 times (DP = 8) and let ZeRO shard optimizer state across the 8 copies.

Flag — "8 + 4 + 2"

The transcript says 64 "is written as 8 + 4 + 2". The degrees multiply: 8 × 4 × 2 = 64. He also describes the layers as "first 25, second 25 of a 100-layer network" while the page uses 96 layers split 24 per stage; he switched to 100 for easy mental maths. The page says 64 H200s; the transcript says "S200", a mis-hearing.

Carry forward

ZeRO asks "where do I store the training state?" TP, PP and CP ask "which GPU computes which part?" The degrees multiply to the GPU count.

9. Second pass: the 30B model's memory bill

The detailed pass uses one model everywhere: 30.2 billion parameters, 96 layers, hidden size 5,120, 40 attention heads of 128 dimensions, and 8 key-value heads.

The training state: 16 bytes per weight

Training one weight takes more memory than the weight itself. The 16-bit weight and gradient are what the matrix multiplications use. The optimizer keeps a 32-bit master copy (small updates would be lost in 16-bit rounding) plus Adam's two running averages.

Where 30.2 billion comes from

The parameter count follows from the shape. Two things set it: how attention shares its keys and values, and how wide the feed-forward block is.

The activations: 127.5 GiB for one sequence

The forward pass stores intermediate results that the backward pass needs to compute gradients. Their size depends on tokens, hidden size and depth, not on the parameter count.

Carry forward

Training state is 450 GiB and one sequence's activations are 127.5 GiB. Both are bigger than an 80 GB card, and they need different fixes: ZeRO for the first, the compute splits for the second.

Jargon — key-value heads (grouped-query attention)

The 40 query heads share only 8 sets of keys and values. Each KV set serves 5 query heads. That makes keys and values one fifth the size of the queries, which matters later for context parallelism and for how far TP can go.

Jargon — FlashAttention

A way to compute attention in small tiles without ever storing the full tokens-by-tokens score table. With it, stored activations grow linearly with sequence length rather than with its square.

Flag — linear, not quadratic

In the transcript he says "16K is not 250, it's going to be way more because it's quadratic" and calls the KV cache "exponential". On the lesson page, with FlashAttention, activations are exactly linear: 8K gives 127.5 GiB, 16K gives 255 GiB, 131K gives 2,040 GiB (16×). What grows with the square of length is the attention compute, and the attention-score memory only if FlashAttention is not used. The transcript also says "30 million parameter", "133 GB for each layer" and "16 238"; these are 30 billion, 1.33 GiB and 16,384.

10. Terminology, link speeds, and why server time is precious

Jargon — the ten terms
  • GPU: one accelerator card. H100: 80 GB (74.5 GiB). B200 (Blackwell generation): 180 GB (167.6 GiB).
  • Node: one machine with 8 GPUs of the same kind.
  • NVLink: the fast wiring between GPUs inside a node. InfiniBand: the network cable between nodes.
  • Micro-batch: the sequences processed in one forward and backward pass (here, one 8,192-token sequence).
  • All-reduce: every GPU contributes a tensor and every GPU gets the combined (summed) result. In a ring of N GPUs each sends 2(N−1)/N times the tensor size, 1.75× at N = 8.
  • All-gather: each GPU contributes a slice, every GPU ends with the full tensor. Reduce-scatter: combine, then each GPU keeps one slice. A ring all-reduce is a reduce-scatter then an all-gather.
  • All-to-all: every GPU sends a different piece to every other GPU. Point-to-point: one GPU sends to one other.
  • Degree: how many GPUs one form of parallelism uses, written like TP = 8.
Flag — two definitions said loosely

The transcript says "all-reduce is taking one and dividing into many". That describes a scatter. All-reduce combines tensors from all GPUs and returns the combined result to all. He also described the global batch as "micro-batch × GPUs in the node"; the page's version (Section 14, step 7) is data-parallel degree × micro-batch × accumulation steps.

An aside on planning experiments. A B200 server takes about 45 minutes to come up the first time, and every failed attempt costs money while no model trains. His comparison was a Bangalore commute: you don't drive to the office for one meeting, drive home, then drive back for lunch. Plan the whole day of experiments before the server starts, log per-layer time and memory in a dry run, and save the logs properly so you don't have to repeat it. He added that Megatron's version and the course's own kernels must stay in sync, which is why they often write their own kernels.

11. Tensor parallelism in detail

Tensor parallelism (TP) splits each layer's matrices so that several GPUs share the work for the same token. This section first shows the idea on a toy feed-forward block small enough to check by hand (Part A), then applies it to the real 30B layer from Section 9 (Part B), and ends with what it saves and what it costs (Part C).

Part A · The idea on a toy block

A1 · The toy block

A feed-forward block expands a token's numbers to a wider middle, then shrinks them back. The toy keeps that shape at tiny size:

The toy uses one expanding matrix and ReLU (negatives become 0). The real block expands with two matrices, gate and up, but the split works the same way.

A2 · On one GPU

Expand: token [1, 1] becomes 4 middle numbers, one per column.

Shrink: the 4 middle numbers become 2 outputs, one per column of the down matrix.

A3 · The same block on 2 GPUs

Expand, split by columns: no talking needed.

Shrink, split by rows: this is where they must talk, once.

A4 · Side by side

Why cut here and not somewhere else

Cutting along the middle keeps every middle number whole on one GPU, so the activation can be applied without asking anyone. Any other cut would leave middle numbers in pieces, and the GPUs would have to add them up before the activation and again at the end, which means two conversations instead of one. This is the Megatron-LM (2019) recipe, and it is what the toy and the real layer both use.

Part B · The real layer (from Section 9)

B1 · The feed-forward block, uncut

B2 · Cut into 8

The natural place to cut is the 16,384 middle numbers. Give each GPU 2,048 of them, and give it only the pieces of the three matrices that touch those 2,048.

B3 · What each GPU does

  1. Every GPU gets the whole token (all 5,120 numbers). This is cheap: it is the same input for all.
  2. Each GPU computes its own 2,048 middle numbers, completely. One middle number needs the whole token and one column of gate and up, and the GPU has both. No talking.
  3. Each GPU applies the activation to its own 2,048 numbers. The activation works on one number at a time, so again no talking.
  4. Each GPU now turns its middle numbers into outputs, and this is where it gets stuck. Every one of the 5,120 output numbers is built from all 16,384 middle numbers, but a GPU has only 2,048 of them. So it can do only its share of each output. Exactly as in the toy (A3): each GPU works out its part of every output, and the parts are added.

So every one of the 5,120 outputs is a sum of 8 parts, one from each GPU. The picture follows output #1.

B4 · Attention, split by head

Attention has four matrices (Section 9). Q, K and V turn the token into a query, key and value for every head. After each head has done its attention, its results are placed side by side (40 heads × 128 = 5,120 numbers) and O mixes them back into the token's 5,120 numbers. Heads never look at each other, so the natural cut is by head. O then plays the role the down matrix played in the feed-forward block.

Toy first: two heads, two GPUs.

The real layer: each GPU gets 5 of the 40 query heads and 1 of the 8 key-value heads.

Why "640 rows of O". O's input is the 5,120 head numbers side by side. GPU 0 produced only heads 1–5, which are numbers 1–640 of that list, so it keeps just the 640 rows of O that multiply them (in the toy, GPU 0 kept rows 1–2 for head 1). Multiplying gives a full list of 5,120 outputs, but each one is only GPU 0's subtotal, exactly like [4, 1, 2, 1] in the toy. One all-reduce adds the 8 GPUs' lists.

In class he pointed out that 56 × 8 ≈ 450: nothing is saved in total, it is spread so each card holds its share. Activations come on top; Section 12 adds them.

C2 · Four all-reduces per layer

Each block (attention, feed-forward) needs one all-reduce going forward, to add the subtotals. Going backward there is one more per block: every GPU used the same token, so each holds only part of that token's gradient, and those parts must be added too.

C3 · How much data, and how long it takes

What travels in one all-reduce is each GPU's list of output parts: 5,120 numbers per token (the [4, 1] and [6, 7] of the toy, at real size). For a whole 8,192-token sequence in 16-bit, that is 8,192 × 5,120 × 2 bytes = 83.9 MB.

A coincidence to avoid mixing up

83.9 MB of traffic and 83.9M weights in one feed-forward matrix are the same number by accident: 8,192 × 5,120 × 2 and 5,120 × 16,384 both equal 83,886,080. One is bytes sent per all-reduce, the other is weights stored.

Megatron-LM's guidance is to keep TP within one server. PyTorch's asynchronous TP hides part of the traffic by sending pieces while the multiplications run (torchtitan measured +12.59% throughput on Llama 3.1 70B across 256 GPUs).

His practical point: the 0.063 s per sequence on B200 is small against a step of roughly 20 seconds, and smaller than the speed differences between GPUs in one node (he joked that one of the 8 GPUs always runs hottest and becomes the slowest). He also said the target of about 1 million tokens per batch, which must stay constant across training stages, will decide which machine they rent.

Flag — per sequence vs per step

The transcript says "56 GB has to travel between each GPU for the full model... 0.06 seconds". The page's 56.4 GB is per sequence; a data-parallel copy processing 32 sequences moves about 1,805 GB per step. The "83 MB of traffic" he mentions is the size of one activation tensor, not the TP traffic total.

Flag — what to compare 0.063 s against

His "20 seconds" is a whole step: a batch of 1 million tokens at the 50,000 tokens per second he quoted from last time (1,000,000 ÷ 50,000 = 20). But the 0.063 s is per sequence, so the fair comparison is the time to process one sequence: 8,192 ÷ 50,000 ≈ 0.16 s. On that basis TP traffic is about 40% of the compute time if none of it overlaps, which is not "penance". His conclusion still holds, because the traffic overlaps with compute and it is small on NVLink, but the margin is closer than the 20-second comparison suggests. It is also unclear from the transcript which model and hardware the 50,000 tokens/s referred to.

Carry forward

TP divides every layer's weights by the degree, and its 56.4 GB per sequence confines it to NVLink.

C · Schedules: same waiting, different memory

The bubble. When the first micro-batch enters stage 0, later stages have nothing to do yet; the same happens in reverse at the end. With p stages and m micro-batches:

waiting share = (p − 1) / (m + p − 1)8 stages: 46.7% at m = 8, 30.4% at 16, 17.9% at 32, 9.9% at 64

This was the point he stressed: the schedule does not make the run faster; it makes it fit. All-forward-then-all-backward cannot run at scale because stage 0 would hold 32 micro-batches (510 GiB). 1F1B holds 8 (127.5 GiB) in the same time.

  • Interleaved 1F1B: each GPU holds several smaller chunks of layers from different parts of the model. Bubble shrinks to (p−1)/(v·m+p−1) (9.9% with 2 chunks), at the cost of more sends and more activation memory.
  • Zero-bubble (Sea AI): split each backward into "gradient for the input" (needed soon by the previous stage) and "gradient for the weights" (can wait). The weight part fills idle slots. ZB-H1 cuts the bubble to one third of 1F1B's; ZB-H2 removes it but holds up to 2p−1 micro-batches.
Flag — two ways to write the bubble

Papers often write the bubble as (p−1)/m, which is waiting divided by working time: 21.9% at 8 stages and 32 micro-batches. The share of the whole step is 17.9%. Same run, two ratios. The transcript's "it will take around eight batches before all GPUs are busy" matches p − 1 = 7 warm-up slots before the 8th stage starts.

Carry forward

More micro-batches shrink the bubble. 1F1B caps each stage's stored activations at the number of stages.

14. Context parallelism: ring, all-gather, Ulysses

Context parallelism (CP) gives each GPU a slice of one long sequence for the whole layer. Everything per-token splits for free; the one problem is attention, where a token must look at earlier tokens that live on another GPU.

D · Load balancing at real scale

Flag — how the ring was described in class

The transcript says "GPU 0 is basically responsible for saving the KV for all the other GPUs" and uses 50,000 tokens per GPU. In a ring every GPU holds its own KV block and passes it on; no GPU stores everyone's KV. The page's CP = 8 example is 16,384 tokens per GPU. He also said the "40 query heads cannot handle it" in a hurry; the page's point is that Ulysses at TP = 8 leaves 5 heads per GPU, which limits the Ulysses degree.

Carry forward

CP splits one long sequence by tokens and only ships keys and values between GPUs. Pair early and late chunks on each GPU, or the last GPU does up to 15 times the attention work of the first.

Topology-aware placement puts the chattiest form on the fastest wire. Nesting from inside out: TP, then CP, then PP, then DP.

For 64 GPUs in 8 nodes: TP = 8 per node on NVLink, DP = 8 across nodes. That gives 72.2 GiB per GPU, too tight for an H100. Sharding the 12 bytes/weight of master copy and Adam state across the 8 DP copies (ZeRO-1) drops state to 19.3 GiB, so 19.3 + 15.9 = 35.3 GiB per GPU. The 8 KV heads also cap TP at 8. On B200 the NVLink:InfiniBand ratio is 18×, and TP = 4 becomes possible (144.4 GiB fits).

Flag — "two seconds times eight"

The transcript estimates that adding nodes costs "2 seconds × 8 = 16 seconds", roughly doubling a 20-second step. That is a back-of-envelope guess, not a page number; the page's 2.11 s is DP gradient traffic over a single InfiniBand card, and it notes real multi-card times are shorter and overlap with the backward pass.

The fraction of the GPUs' peak arithmetic that the training run actually uses. 40% means 60% of the theoretical compute is lost to communication, waiting and memory traffic. It is a metric, not a benchmark.

17. Self-study: DeepSeek V3, V4, V4.1-Flash

He called these sections optional, and said DeepSeek is worth studying because it is one of the few labs publishing how it speeds up training. He also noted that recent training papers are coming mainly from Chinese labs rather than US ones.

DeepSeek-V3 and expert parallelism

A mixture-of-experts (MoE) layer has many small feed-forward networks (experts); a router sends each token to a few of them. Expert parallelism (EP) places different experts on different GPUs. His example: 800 experts on 8 GPUs, 100 each, with only 1% active per token. Most expert matrices sit idle, so placement matters; ideally similar experts would live together, but experts are not assigned by topic.

V3 (671B total, 37B active per token, 2,048 H800 GPUs) used PP = 16, EP = 64 across 8 nodes, ZeRO-1, and no tensor parallelism. The H800's NVLink is only about 3.2× faster than InfiniBand, which removes TP's main advantage. Each token is limited to 4 nodes. DualPipe feeds micro-batches in from both ends of the pipeline and overlaps expert communication with compute; it keeps two copies of the parameters. V3 ran its linear layers in FP8, with 2,788K H800 GPU-hours total. Kimi K2 (over 1T parameters) rejected DualPipe because of that doubled parameter memory and used interleaved 1F1B.

DeepSeek-V4

  • Muon with whole matrices. Muon is an optimizer that computes each update from a whole weight matrix, so it cannot be sharded piece-wise like Adam state. V4 assigns each dense matrix whole to one GPU, balanced across GPUs (under 10% extra memory). He said V5 will compare AdamW against Muon and noted Muon keeps less optimizer state.
  • Two-stage context parallelism for compressed sparse attention: first hand the boundary entries to the next GPU so compression blocks aren't cut, then all-gather the compressed entries.
  • Manifold-constrained hyper-connections: the residual stream is widened into 4 parallel copies, which adds pipeline traffic; fused kernels and schedule changes hold the extra cost to 6.7%.

DeepSeek-V4.1-Flash

The upper 20 of its 40 layers compute keys and values from the output of layer 20 (a design derived from YOCO, "You Only Cache Once"). That saves a lot of memory in serving, but in training a pipeline cut can separate the layer that produces the shared state from the layers that read it, so each shared tensor needs an owner stage and a lifetime.

19. Reversibility: the idea

Every technique so far spreads activations across more GPUs. A reversible network removes most of them instead. The forward pass keeps only the states at the boundaries of the stack. The backward pass rebuilds each layer's input from its output when needed, by running the layer's update in reverse.

The method (Gal, Eliasof, Turek, Ascher, Treister, Haber; arXiv, late 2025) treats layers as time steps and uses the midpoint rule. Write pℓ for the residual stream entering layer ℓ and f for the whole transformer block (attention then feed-forward):

forward:  pℓ+1 = pℓ−1 + 2h · f(pℓ)
backward: pℓ−1 = pℓ+1 − 2h · f(pℓ)h is a fixed step size. The block is evaluated at the middle state, which the backward pass already holds.

Why an ordinary block is not reversible. An ordinary block computes pℓ = pℓ−1 + f(pℓ−1). To undo it you need f(pℓ−1), but pℓ−1 is exactly what you are trying to recover. The midpoint rule avoids this by adding f to the state two layers back and evaluating f at the state in between.

A tiny example you can check by hand

Let each "layer" be f(p) = p, and 2h = 1. Start with p0 = 1, p1 = 1.

Not the same as recomputation (activation checkpointing). Recomputation stores the input of every group of layers and re-runs them forward in backward. A reversible stack stores no layer inputs; it rebuilds them by running the rule backward. Memory for activations becomes independent of depth: a 96-layer and a 20-layer model store the same two boundary states.

Costs and constraints.

  • Compute: every block runs one extra time in backward. The paper estimates 30–50% overhead; the page says "about a third"; the instructor said "at least 30 to 40% slower".
  • Deterministic forward: dropout must be 0, because the rebuilt activations must match the forward ones exactly and a random mask cannot be replayed.
  • Marginal stability: the step size and coefficients must sit in a narrow range, or training is hard.

The paper's evidence: on an 80 GB H100 the standard model fit batch 26, the reversible one 257 (9.88×). At 96 layers with hidden size 512, 874 vs 52 batch, giving 114.49 vs 56.96 samples/s: faster overall, because the much bigger batch outweighs the extra compute.

Flag — "three methods" and "Euler"

He said the paper "has three methods" and for the assignment named "Euler" ("boiler/oiler" in the transcript) and midpoint. The paper's three are midpoint, leapfrog (a second-order version) and Hamiltonian (two coupled streams). A plain Euler step is the ordinary residual block, which is not reversible. In the Lightning LM configuration "Euler" appears as the bootstrap: how the second starting state p1 is made from p0. What "Euler variant" should mean is an open call in A7.

Flag — "memory is the same for a thousand or a billion tokens"

That line in the transcript overstates it. Reversibility removes the dependence on depth. The boundary states and the one layer being rebuilt still grow linearly with tokens (next section: 1.5 GiB at 8K, 23.8 GiB at 131K).

20. What reversibility changes

For the 30B model, a reversible stack stores two boundary states (2 × tokens × 5,120 × 2 bytes) plus the working memory of the one layer being rebuilt (1.33 GiB at 8K).

Reversibility does not make memory free. It moves the binding constraint from activations to the training state, which changes the order of decisions:

  • TP: unchanged; weights are still there to divide.
  • SP: now only divides the small boundary states.
  • PP: loses one of its two reasons (dividing activations by layer).
  • CP: needed only at much longer sequences, roughly two orders of magnitude later.
  • ZeRO: becomes more important, since state now fills the card. Under ZeRO-3, the rebuild in backward is a second forward, so parameters must be gathered again for it.

Lightning LM (the instructor's own report) is the at-scale evidence: a 120B sparse MoE with 20 layers, hidden 4,096, sequence 8,192, trained on one node of 8 GPUs at a measured peak of about 256 GB per GPU. Its 9B model at 8K used 130.9 GB per GPU vs an estimated 550–650 GB with stored activations. Its 2B model at 4,096 tokens on eight 40 GB A100s trained at batch 32 with reversibility, while above 8 did not fit without it. Settings: step size 0.25, blend coefficient 0.5, with the note that library defaults differ.

In class he walked through the growth path (2B → 5B → 9B → 120B, each initialised from the last) and the limits he stated plainly: numbers above 40 GB are estimates of runs never made, and when memory is not the bottleneck reversibility just slows you down. The 2B model on 80 GB cards trained faster without it.

  • The 2B model "took 73 GB" in the transcript; the page does not give that figure.
  • He said reversibility forbids weight decay as well as dropout. The page and the paper only require zero dropout. Carry forward

Reversibility trades roughly a third more compute for activation memory that does not grow with depth. This moves the bottleneck to the training state and changes which form of parallelism you need first.

A2. What the three runs are really measuring

The point of the assignment is to see the paper's result yourself: reversibility costs speed per token at the same batch, but frees so much memory that a much larger batch fits, and the larger batch can win back the speed. The results depend on how much of your GPU memory is activations that reversibility can remove.

That is the catch for a 20M model. With GPT-2's 50,257-token vocabulary, the logits (one score per vocabulary word, for every token in the batch) are often the biggest thing in memory, and reversibility does nothing for them.

With the GPT-2 vocabulary, logits (about 7.7 GiB) outweigh block activations (1–3 GiB). Reversibility would remove the 1–3 GiB and leave the 7.7 GiB, so the maximum batch would grow only modestly, not the paper's ~10×. Two ways to fix this, both reasonable:

  • Chunked cross-entropy: compute the loss over the vocabulary in slices so the full logits tensor never exists at once. You built this in Session 9.
  • A smaller vocabulary (for example an 8K-token BPE trained on the corpus), which shrinks logits about 6× and puts most of "20M" into the transformer blocks.
Why this matters

Without handling logits, the headline finding would be "reversibility barely helps", and that would be a finding about the output layer, not about reversibility. Reporting a memory breakdown (state, block activations, logits) for each run makes the result clear either way.

A8. Decision 5: how the memory saving is actually made

This is the easiest part to get wrong. If you write the midpoint rule as ordinary PyTorch code, autograd still stores every layer's activations. The architecture would be reversible, but no memory would be saved. The saving only happens if the stack is wrapped in a custom torch.autograd.Function:

Two gates before any GPU time:

  • Gradient gate: the same reversible model run through plain autograd (stores everything) and through the custom function (stores nothing) must give matching gradients, in fp64 on CPU to a tight tolerance, then in mixed precision with the measured gap reported.
  • Reconstruction gate: the rebuilt p0 must match the real p0, and its error is reported per layer. This is what will reveal the precision drift from A6.

Dropout is 0 in all runs, including the baseline, so the comparison stays fair.

A9. Decision 6: batch sizes and a fair comparison

  • Baseline batch B. "Fix a batch size you can run." I suggest B = the largest power of two the baseline fits (found by the probe), so run A is a fair best effort and not handicapped.
  • Runs B and C use the same B, same seed, same data order, same learning rate schedule. Only the architecture changes.
  • Maximum batch for run D. Found by a binary search on real forward and backward steps, leaving about 10% headroom. We also record the baseline's maximum, so the report can give a ratio like the paper's 9.88×.
  • Learning rate at the bigger batch. 50M tokens are fixed, so a batch 8× larger means 8× fewer optimizer steps. With the same learning rate, run D may show a higher final loss purely because it took fewer steps. Three choices: keep LR (simplest, and itself a finding); scale LR by √(batch ratio) (a common rule); or a short LR sweep (most work).

My recommendation: √ scaling for run D, plus reporting loss against tokens seen (not steps), so all four curves share one x-axis.
